# Enterprise Architecture & Service Boundaries

## 1. Overview
The National Material Intelligence & Harmonization Platform is an enterprise-grade web application built to ingest, normalize, semantically match, and govern CPSE material master data.

To ensure long-term maintainability, the platform is structured as a strict **Monorepo** with heavily enforced service boundaries. Code across domains (e.g., UI, Database, AI) must only communicate through explicitly defined APIs or Python function contracts.

## 2. Core Service Boundaries

### `frontend/` (UI Layer)
- **Role**: Presentation layer and user interaction.
- **Rules**: Zero business logic. Must consume backend via REST (`/api/v1`).
- **Stack**: React, TypeScript, Vite, Tailwind, React Router, TanStack Query, React Hook Form, Zod.

### `backend/` (API & Business Logic)
- **Role**: State orchestration, request validation, integration routing.
- **Rules**: Serves as the sole orchestrator. Connects to `database/` for persistence, calls `ai/` for semantic matching, and exposes endpoints to `frontend/`.
- **Sub-boundaries**:
  - `app/api/`: FastAPI route controllers.
  - `app/services/`: Core business workflows (Approval workflow, National Code minting).
  - `app/schemas/`: Pydantic validation for all inbound/outbound communication.
  - `app/core/`: Security, authentication, and RBAC implementation.
- **Stack**: Python, FastAPI, Pydantic.

### `database/` (Data Access Layer)
- **Role**: Immutable persistence and generic query interfaces.
- **Rules**: Handles all PostgreSQL/SQLAlchemy dialect logic. Exposes generic `CRUDBase` repositories. Backend services import these repositories.
- **Stack**: PostgreSQL, pgvector, SQLAlchemy, Alembic.

### `ai/` (Intelligence Layer)
- **Role**: Stateless normalization, embedding vectorization, and language model interaction.
- **Rules**: Must NEVER instantiate a database connection. Exposes pure Python functions (e.g., `calculate_similarity(mat_a, mat_b)`) that return strongly typed Pydantic models. 
- **Stack**: Python, sentence-transformers, LLM SDKs (OpenAI/Anthropic).

### `integrations/` (Enterprise Adapters)
- **Role**: Extract, Transform, Load (ETL) adapters for legacy CPSE systems.
- **Rules**: Connects to external systems (or the `mock-erp`) to transform proprietary tabular structures into the platform's standardized `SourceMaterial` format.

### `infrastructure/` (DevOps & Deployment)
- **Role**: Containerization and observability.
- **Rules**: Stores Dockerfiles, `docker-compose.yml`, Redis configs, and Prometheus/Grafana dashboards.

## 3. The 12 Immutable Architectural Principles

All engineers contributing to this repository must adhere strictly to these principles:

1. **AI never directly owns authoritative data.** The AI generates *candidates* and *recommendations*, which are queued for review or silently appended as metadata.
2. **LLM outputs must be schema validated.** Any text generated by an LLM must pass through strict `Pydantic` schema verification (via `instructor` or constrained decoding) before touching the application layer.
3. **Source data is immutable.** A `SourceMaterial` record from a CPSE represents physical truth and cannot be modified or overwritten.
4. **National Material Codes are backend controlled.** Only the Backend deterministic `services/` logic possesses the authority to mint a new National Material Code. AI cannot hallucinate codes.
5. **Semantic similarity does not equal engineering equivalence.** Two materials might mathematically embed closely (e.g., a 10mm pipe vs a 12mm pipe), but their functional disparity means they are physically incompatible.
6. **Critical attributes can override AI similarity.** Deterministic rules (e.g., `voltage` mismatch on a motor) act as an absolute veto against high-confidence AI semantic matches.
7. **Human approval controls risky decisions.** Conflicts and near-duplicates must route through the RBAC approval pipeline before altering the National catalog.
8. **All important changes are auditable.** Approvals, rejections, and mapping alterations must log the user ID, timestamp, and context to the `AuditLog` table.
9. **CPSE data access must be authorization controlled.** Users can only see data associated with their specific CPSE unless granted global admin privileges.
10. **No fake SAP integration claims.** Do not hardcode fictitious SAP BAPI success responses. All external integrations must use explicit Mock APIs clearly demarcated as development mocks.
11. **Frontend must use real APIs.** The React application cannot bypass the network layer by reading JSON files directly. It must fetch data natively through the `backend/` FastAPI layer.
12. **Configuration must not be hardcoded into visual components.** UI strings, environments, and business thresholds (like confidence scores) must be dynamically pulled from `.env` or application config files.
